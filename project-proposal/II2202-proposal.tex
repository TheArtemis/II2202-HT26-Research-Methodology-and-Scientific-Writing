\section{Introduction}

\subsection{Background, Rationale, and Related Work}
Various distributed systems, such as databases, distributed file systems, and cluster membership frameworks, rely on consensus protocols to find agreement on a shared state.
Raft, one of the most widely used consensus protocols to-date, is a leader-based protocol: the leader node appends client entries to its log and replicates them to its followers.
An entry is then considered committed once a majority of all nodes (including the leader) have stored such entry.
The protocol is designed to remain safe under arbitrary message delay and can stay live as long as the leader can talk to a each follower in a majority quorum directly.

The consequences of complete network partitions are well understood. If connections to minority of nodes are lost, they can be treated as crashed nodes and the protocol will continue to operate correctly.
Converseley, if connections to a majority of nodes are lost, the any consensus protocol will fail to make progress.

However, partial network partitions present more challanges in Raft. Specifically, a partial partition is a change in network topology where nodes are still, through other nodes, connected to each other, but some direct links between nodes are lost~\cite{jensen2021raft,alfatafta2020nifty}.
Raft, however, assumes point-to-point links between participating nodes. A leader that loses direct contact with two followers may be unable to form a quorum, even though both followers could still be reached via a third replica if packets were forwarded through that intermediate node at the network layer.

Prior work has looked at this problem from several angles. Jensen, Howard, and Mortier~\cite{jensen2021raft} studied etcd/Raft during partial network failures and reported election instability. They mention overlay routing as a possible solution to partially partitioned network topologies in Raft, for example, routing traffic between two replicas through a third. However, they do not implement or measure that approach.
Alfatafta et al.\ introduced Nifty, a transparent communication layer that detours packets around failed paths~\cite{alfatafta2020nifty}. Nifty showed that such routing can mask partial partitions with slight overhead in several systems, and while the authors discuss Niffty's application to Raft, it was never included in their evaluation.
Omni-Paxos~\cite{ng2023omnipaxos} takes a different route by changing the consensus protocol itself to handle partial connectivity. Particularly, the author proposes a notion of quorum-connectivity - stronger abstraction than the classical majority quorum which additionally to the requirement of having a majority of non-faulty nodes, requires that all nodes in the quorum are reachable from each other.
OmniPaxos paper also discusses the option of using a transparent network overlay to mask partial partitions in consensus protocols. However, it claims that introduction of such overlay could lower the levels of performance and fault-tolerance of the consensus. However, the authors do not provide the evaluation of such claim and leave it as a future work.

Together, these papers suggest that transparent multi-hop routing could help Raft in partially connected networks, but they leave open how large the benefit is, when it appears, and what it costs in commit latency. This project focuses on such identified gap in evaluation of transparent multi-hop routing for Raft under partial network partitions.

\subsection{Research Problem, Aim, and Research Questions}

\textbf{Research problem.}
Existing work shows that Raft can struggle under partial connectivity, that transparent routing can mask such partitions in general, and that overlays may trade extra reachability for higher latency~\cite{jensen2021raft,alfatafta2020nifty,ng2023omnipaxos}. What is still missing is a controlled, topology-level picture for Raft: which partially connected graphs regain progress when multi-hop forwarding is enabled, which routed paths actually matter for commits, and how much latency that introduces.

\textbf{Aim.}
We aim to experimentally characterize transparent multi-hop routing as a network-layer resilience mechanism for Raft, without changing the consensus implementation itself.

\textbf{Research questions.}
\begin{enumerate}
  \item \textbf{RQ1 (Liveness):} Under which partial-connectivity topologies does transparent multi-hop routing restore stable Raft progress compared with direct communication only?
  \item \textbf{RQ2 (Latency):} How does the route stretch of quorum-critical follower paths affect Raft commit latency?
\end{enumerate}

These questions are scoped to a five-node cluster and a small set of representative topologies, which we believe is enough to obtain paired direct-vs-overlay comparisons rather than exhaustive graph enumeration.

\textbf{Hypotheses.}
We expect transparent forwarding to restore progress when the routed graph gives a viable leader stable bidirectional paths to a majority (H1). Commit-latency overhead should follow the slowest follower needed for the fastest available majority, not the average hop count across the cluster (H2).

\section{Proposed Research Method}

\subsection{Research Design and Methodological Rationale}

We will study this experimentally on a small emulated cluster. Five Raft nodes run on a single host, wrapped around a controlled network infrastructure, so that we can break individual links while leaving other physical paths available. Each topology is run twice: once with ordinary direct communication, and once with transparent multi-hop forwarding.

This setup will allow us to answer the research questions as we will be able to control the topology, the delay, and the failure timing, and we will be able to compare liveness and latency under those same conditions.

For latency, a simple rule of thumb is enough to interpret the results. A cluster of $N$ nodes commits an entry once a quorum of $q = \lfloor N/2 \rfloor + 1$ members have stored it. With a stable leader, the leader already counts toward that quorum, so the delay is largely set by the $(q-1)$-th fastest follower acknowledgement. A multi-hop route therefore matters most when the forwarded follower is among the slowest paths still needed for the majority, not when it is just an extra hop somewhere in the cluster.

\subsection{Experimental Setup and Topologies}

We plan to use a production-grade Raft implementation, most likely etcd, and keep its configuration fixed throughout, including any extra mechanisms such as PreVote or CheckQuorum. Link delay and loss will be injected with Linux \texttt{tc/netem}, and partial cuts with namespace routing or firewall rules. Forwarding itself will be done with ordinary IP routing or a small relay, so that Raft still addresses the same logical endpoints. A simple closed-loop client will issue small sequential writes and record when each request is submitted and when the commit is acknowledged.

Table~\ref{tab:topologies} shows the topologies we intend to run. T0 is a healthy baseline. T1 breaks a direct path that the leader does not actually need for a quorum, so little should change. T2 is the case that matters most for RQ1: the leader loses enough direct contacts to stall, but the missing followers can still be reached through a relay, so overlay routing should restore progress. T3 is a more awkward chained or asymmetric cut, where only one bridge node joins the two sides, to see how sensitive leader stability and latency are to the shape of the graph.

What we vary is the routing mode (direct versus overlay), the topology (T0--T3), the one-way delay on each hop (0.5\,ms, 5\,ms, and 20\,ms, standing in for local, moderate, and WAN-like conditions), and how many physical hops a quorum-critical follower is away. What we measure is whether writes keep committing during the failure, how long any stall lasts, how quickly commits resume, whether the leader or term changes, and the commit latency seen by the client (median and tail). Throughput is only a secondary check.

\subsection{Work Procedure and Data Collection}

Every run follows the same script. We start from T0, wait until there is a stable leader, collect a short baseline, then inject the chosen link failures without changing membership, and keep the workload going for the rest of the trial. 

Each topology is done once with direct communication and once with overlay routing. Overlay runs also sweep the three delay settings, while Raft continues to use the same peer addresses. We repeat each configuration five times with controlled timing and summarize the results with medians and percentile ranges.

A single-host emulation will not capture every effect of a real multi-machine deployment. We mitigate this by injecting controlled delay and reporting how busy the host is. Results may also depend on which Raft implementation we pick and how it is tuned. We are not trying to cover all graphs; the point is to characterize the mechanism, not to enumerate every partial partition. If routing itself takes time to converge, we will either preconfigure the alternate paths and switch them on in a controlled way, or measure that setup time separately from Raft's recovery. Safety is assumed as long as the overlay still delivers reliable point-to-point messages. The experiment itself is about availability and performance.

\subsection{Planned Data Analysis}

The main comparisons are always the same topology and delay, with and without overlay routing. The figures we expect to produce are commits over time around the failure, recovery time by topology, commit-latency distributions grouped by how stretched the route is, and leader or term changes in each run. A useful extra variable is whether the routed follower belongs to the fastest majority the leader can form. That should help explain cases where routing brings liveness back without much extra delay.

We will treat the project as successful if we find at least one topology where direct-only Raft stops making sustained progress while transparent routing restores it, and if we can report commit-latency distributions under at least three delay settings. A negative result would also be useful. For example, if election churn dominates, extra reachability alone may not be enough to stabilize the cluster.
