\section{Introduction}

\subsection{Background, Rationale, and Related Work}

Distributed systems often rely on consensus protocols to replicate state across replicas. Raft is a widely used leader-based protocol: the leader appends client operations to its log and replicates them to followers, and an entry is committed once a majority of the cluster has stored it~\cite{ongaro2014raft}. The protocol is designed to remain safe under arbitrary message delay and can stay live as long as the leader can talk to a quorum.

Complete network partitions are relatively well understood. If a minority of replicas is cut off, they can be treated much like crashed nodes. Partial partitions are trickier. The communication graph may still be connected, yet some replica pairs cannot reach each other directly~\cite{jensen2021raft,alfatafta2020nifty}. In that situation, end-to-end connectivity may exist through intermediate nodes even when direct links fail. Raft, however, assumes peers communicate point-to-point. A leader that loses direct contact with two followers may be unable to form a quorum, even though both followers could still be reached via a third replica if packets were forwarded transparently at the network layer.

Prior work has looked at this problem from several angles. Jensen, Howard, and Mortier~\cite{jensen2021raft} studied etcd/Raft during partial network failures and reported election instability. They mention overlay routing as a possible remedy---for example, routing traffic between two replicas through a third---but they do not implement or measure that approach. Alfatafta et al.\ introduced Nifty, a transparent communication layer that detours packets around failed paths~\cite{alfatafta2020nifty}. Nifty showed that such routing can mask partial partitions with modest overhead in several systems, and the authors discuss LogCabin (an early Raft implementation), but Raft was not part of their performance evaluation. Omni-Paxos~\cite{ng2023omnipaxos} takes a different route by changing the consensus protocol itself to handle partial connectivity. Its evaluation contrasts protocol-level fixes with transparent overlays and points out that masking connectivity through relays can add hops to the commit path and create shared failure dependencies when one relay carries several logical links.

Together, these papers suggest that transparent multi-hop routing could help unmodified Raft in partially connected networks, but they leave open how large the benefit is, when it appears, and what it costs in commit latency and fault tolerance. This project focuses on that gap for vanilla Raft rather than proposing a new consensus algorithm.

\subsection{Research Problem, Aim, and Research Questions}

\textbf{Research problem.}
Existing work shows that Raft can struggle under partial connectivity, that transparent routing can mask such partitions in general, and that overlays may trade extra reachability for higher latency and relay dependencies~\cite{jensen2021raft,alfatafta2020nifty,ng2023omnipaxos}. What is still missing is a controlled, topology-level picture for unmodified Raft: which partially connected graphs regain progress when multi-hop forwarding is enabled, which routed paths actually matter for commits, and how much latency and correlated failure risk that introduces.

\textbf{Aim.}
We aim to experimentally characterize transparent multi-hop routing as a network-layer resilience mechanism for vanilla Raft, without changing the consensus implementation itself.

\textbf{Research questions.}
\begin{enumerate}
  \item \textbf{RQ1 (Liveness):} Under which partial-connectivity topologies does transparent multi-hop routing restore stable Raft progress compared with direct communication only?
  \item \textbf{RQ2 (Latency):} How does the route stretch of quorum-critical follower paths affect Raft commit latency?
  \item \textbf{RQ3 (Fault tolerance):} How does routing several logical Raft links through the same relay change the cluster's sensitivity to later node failures?
\end{enumerate}

These questions are scoped to a five-node cluster, a small set of representative topologies, and roughly 80 hours of work, which we believe is enough to obtain paired direct-vs-overlay comparisons rather than exhaustive graph enumeration.

\textbf{Hypotheses.}
We expect transparent forwarding to restore progress when the routed graph gives a viable leader stable bidirectional paths to a majority (H1). Commit-latency overhead should follow the slowest follower needed for the fastest available majority, not the average hop count across the cluster (H2). If several logical links share one relay, failing that relay should remove multiple paths at once and reduce effective fault tolerance (H3).

\section{Proposed Research Method}

\subsection{Research Design and Methodological Rationale}

We will use a controlled emulation study. A five-node Raft cluster runs inside emulated network namespaces (or Mininet~\cite{lantz2010mininet}) on a single host, where we can fail individual links while keeping alternative physical paths available. Each scenario is run twice: once with direct-only networking and once with transparent multi-hop forwarding that leaves Raft peer addresses unchanged.

This design fits the research questions because we need repeatable control over topology, delay, and failure timing, and we need paired measurements of liveness and latency under the same conditions. A purely analytical approach would struggle to capture Raft's election and leader-change behaviour, which prior work shows can dominate partial-partition outcomes~\cite{jensen2021raft}. Modifying Raft itself, as in Omni-Paxos~\cite{ng2023omnipaxos}, would answer a different question---we deliberately keep the protocol fixed so that any differences can be attributed to the network layer.

As a simple guide for interpreting latency results, note that for $N$ replicas a commit needs a quorum of $q = \lfloor N/2 \rfloor + 1$ members. With a stable leader, network-dominated commit latency is roughly set by the $(q-1)$-th fastest follower acknowledgement path, because the leader already counts toward the quorum. A multi-hop route therefore matters most when the forwarded follower is among the slowest paths required for the majority.

\subsection{Experimental Setup and Topologies}

\textbf{Platform.}
The cluster will use an unmodified Raft implementation (likely etcd or another production-grade baseline) with fixed configuration throughout the project, including any extensions such as PreVote or CheckQuorum. Linux \texttt{tc/netem} will inject per-link delay and loss; namespace routing or firewall rules will create asymmetric or pairwise link failures. Transparent forwarding will be implemented with IP routing or a small relay layer so that Raft continues to address the same logical endpoints. A closed-loop client will issue small sequential writes, recording timestamps at submission and commit acknowledgement.

Table~\ref{tab:topologies} lists the scenarios we plan to run. T0 calibrates the healthy baseline; T1--T4 cover the fault cases of interest.

\textbf{Independent variables.}
Routing mode (direct-only vs.\ transparent forwarding), topology (T0--T4), per-hop one-way delay (0.5\,ms, 5\,ms, and 20\,ms as local, moderate, and WAN-like conditions), and route stretch for followers that must be reached via one to three physical hops.

\textbf{Metrics collected.}
We will record the fraction of writes committed during failure windows, duration of zero-progress intervals, recovery time from fault injection to sustained commits again, leader/term changes, client-observed commit latency (p50, p95, p99, and max), throughput as a secondary measure, and the effect of failing a relay after the overlay has restored progress.

\subsection{Work Procedure and Data Collection}

Each experiment follows the same sequence. We warm up the cluster under T0 and confirm a stable leader, run a fixed pre-fault interval to collect baseline metrics, inject the chosen link failure(s) without changing membership, and then run the workload for the remainder of the trial. Every topology is executed once in direct-only mode and once with transparent routing; overlay runs additionally sweep per-hop delay while keeping logical Raft addresses fixed. For T4, the relay is failed only after commits have resumed. Each configuration is repeated at least five times with controlled timing, and we summarize results with medians and percentile ranges.

\textbf{Scope and limitations.}
Single-host emulation will not capture every effect of a real multi-machine deployment; we mitigate this by using controlled delay injection and reporting host resource use. Results may also depend on the specific Raft implementation and its tuning. The topology set is not meant to cover all graphs---the goal is to characterize the mechanism, not to enumerate every partial partition. Routing convergence could affect recovery time; we plan either to preconfigure alternate routes and activate them deterministically or to measure routing setup separately from Raft recovery. Safety is assumed as long as the overlay preserves reliable point-to-point delivery; the experiment focuses on availability and performance.

\subsection{Planned Data Analysis}

Analysis will emphasize paired comparisons between direct and overlay modes for the same topology and delay setting. The main figures we expect to produce are: commits over time around fault injection, recovery time by topology, commit-latency distributions grouped by route stretch, and leader/term changes during each run. A useful derived variable is whether a routed follower belongs to the fastest majority needed for commit; this should help explain cases where routing restores liveness without much latency penalty.

The project will be considered successful if we find at least one topology where direct-only Raft loses sustained progress while transparent routing restores it, and if we can report commit-latency distributions under at least three delay settings. A stronger outcome would additionally show that failing a shared relay removes several logical paths at once. A carefully controlled negative result would also be informative---for example, if election churn dominates and routing reachability alone is not enough to stabilize progress.
